## 1. 总体策略

```text
功能四阶段（Phase 0–4）     →  技术/功能基线（可内测、可演示主路径）
        ↓ 全部完成并验收
产品级开发（商业化迭代）   →  可售、可稳、可续的商业 v1.0+
```

| 阶段 | 目标 | 验收口径 |
|------|------|----------|
| **Phase 0–4** | 多开 + 伪装 + 相机 + 基础发布准备 **真能用** | 功能门禁（见各 Phase 执行计划） |
| **产品级开发** | 授权、安全、合规、质量 SLA、运维发版 | **商业 Go-Live 门禁**（本文第 5 节） |

### 1.1 原则

1. **先底座、后商业**：四阶段未全部完成前，**不进入**产品级/商业化主开发（可做接口预留与文档规划）。  
2. **四阶段不是 Demo 糊弄**：实现须可支撑后续商业化（真引擎、真 Hook、模块可替换），避免推倒重来。  
3. **四阶段完成 ≠ 可售**：仅表示功能基线达成，可开始产品级迭代。  
4. **商业完成以 Go-Live 门禁为准**，不以「Phase 勾选」单独作为售卖依据。

## 2. 功能四阶段（底座）摘要

| 阶段 | 内容 | 商业含义 |
|------|------|----------|
| Phase 0 | UI + Fake 引擎 | 产品壳与配置模型 |
| Phase 1 | BlackBox 真多开 | 核心卖点：多开隔离 |
| Phase 2 | 定位 / 设备 / 网络伪装 | 核心卖点：环境伪装 |
| Phase 3 | 虚拟相机 + 授权能力雏形 | 场景能力 + 本地授权骨架 |
| Phase 4 | 兼容回归、混淆、协议页、RC | 内测/预发布质量 |

**退出条件与当前状态：**

- [x] Phase 0–4 执行计划 / Backlog 对应 Epic 均验收通过
- [ ] 主路径真机（在「通用机型策略」下，见第 3 节）可回归  
- [x] 已知问题与不支持列表成文（含系统版本）
- [x] 架构仍满足：UI → `SandboxEngine`，便于加固与替换

商业授权 P-A 已作为独立工作包提前完成。主路径真机 ST-2 尚未完成，因此
不得据此宣称满足商业 Go-Live 门禁。

## 3. 机型与测试策略（产品约束）

### 3.1 机型范围（当前约定）

| 项 | 约定 |
|----|------|
| **优先范围** | **通用机型**（AOSP/接近原生、主流品牌未深度定制或可代表通用行为的机型） |
| **首期不做** | 穷尽全品牌 ROM 定制适配；不承诺全机型 |
| **系统** | 以四阶段主目标为准（如 Android 10–13 优先）；14/15 记入已知问题或后续迭代 |

「通用机型」落地时建议固定一份短名单（示例，可调整）：

- 1～2 款接近原生的真机（如 Pixel 系或未深度改系统的机型）  
- 1 款主流品牌「相对通用」真机（可选）  
- **不以奇葩定制 ROM 为阻塞**

### 3.2 测试顺序（强制）

```text
1. 模拟器 / 通用系统镜像 测试通过
        ↓
2. 通用真机 测试通过
        ↓
3. （产品级阶段）扩大机型与目标 App 抽样
```

| 步骤 | 要求 |
|------|------|
| **先模拟器** | 功能开发与提测默认先在模拟器跑通主路径与冒烟 |
| **后真机** | 模拟器通过后，再在约定通用真机上验证多开/伪装等 |
| **失败处理** | 模拟器不过不进真机；真机不过不宣布该 Phase/版本通过 |

### 3.3 四阶段 vs 产品级在测试上的差异

| | 四阶段 | 产品级 |
|--|--------|--------|
| 机型 | 通用 + 模拟器优先 | 在通用基线上扩展清单与占比 |
| 目标 App | 轻量/可测应用为主，强检测记问题 | 按卖点定义目标 App 清单与通过率 |
| 通过标准 | 功能可用 | 功能 + 稳定 + 授权 + 合规 + 运维 |

## 4. 产品级开发（四阶段之后）做什么

进入产品级后，按优先级推进（详见 `15_产品级开发计划.md`）：

| 序 | 工作包 | 说明 |
|----|--------|------|
| P-A | 商业授权 | **已完成**：服务端发卡/绑定/解绑、RSA 离线 Token、客户端激活与刷新 |
| P-B | 安全加固 | Release 混淆强化、加固、防二次打包、密钥 |
| P-C | 质量 SLA | 成功率、崩溃、回归脚本、兼容矩阵扩充 |
| P-D | 合规分发 | 协议、隐私、权限与渠道政策、LICENSE |
| P-E | 观测与发版 | 崩溃上报、版本更新、灰度 |
| P-F | 卖点增强 | 地图/轨迹、14/15、蓝牙等（按市场优先级） |

**启动条件：** 第 2 节退出条件全部满足，产品/负责人书面确认「进入产品级开发」。

## 5. 商业 Go-Live 门禁（可售卖前）

以下不满足则 **不宣称商业 v1.0 可售**：

### 5.1 P0（必须）

- [ ] 通用机型 + 约定系统上，多开主路径稳定（导入/启动/克隆/清数据/卸载/快捷方式）  
- [ ] 伪装与相机达到产品定义的「可用」标准（有探针/抽检记录）  
- [ ] **服务端商业授权**上线（非仅本地 DEV 卡密）  
- [ ] Release 安全底线（混淆 + 约定加固策略）  
- [ ] 隐私政策 / 用户协议 / 权限说明齐备  
- [ ] 依赖 LICENSE 与商用合规有结论  
- [ ] 崩溃采集与发版通道可用  

### 5.2 P1（首发可弱但有计划）

- [ ] 更新策略、解绑客服流程  
- [ ] 机型/目标 App 矩阵持续扩充  
- [ ] Android 新版本跟进节奏

```text
M0  文档与策略冻结（本文 + 15）
M1  Phase 0 完成

M9+ 运营迭代（适配、对抗、卖点）
```

## 7. 明确不做（避免范围漂移）

| 四阶段内不做 | 产品级前不做 |
|--------------|--------------|
| 完整商业中台 | 全品牌 ROM 穷尽适配 |
| 以强检测 App 为唯一验收 | 无基线的大规模投放 |
| 未授权 VA 源码 | 无门禁的「先卖再说」 |

---

## 8. 一句话

> **先完成功能四阶段并按通用机型「模拟器 → 真机」验收；全部通过后进入产品级开发，补齐授权、安全、合规与运维，再以 Go-Live 门禁作为商业可售标准。**
