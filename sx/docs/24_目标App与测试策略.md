## 1. 钉钉是不是默认目标？

### 结论：**不是。**

| 点 | 说明 |
|----|------|
| **现状** | 闪现（sx）文档与实现 **从未把钉钉定为默认/唯一目标 App** |
| **现能力** | 沙箱多开 + 通用 Hook（定位/设备/网络/Camera1 PreviewCallback 等），**面向「任意装进沙箱的第三方 App」**，不是钉钉专用插件 |
| **星盒 (xh)** | 商业产品常 **按办公场景（含钉钉等）打磨对抗与相机路径**；那是竞品能力，**不等于 sx 已默认对齐钉钉** |
| **为何 sx 像「没疑问」** | 阶段门禁刻意写成「轻量/可测路径、强检测不保证」，避免未定义清单却宣称「过钉钉」 |

### 和钉钉的关系（规划）

```text
通用能力（现在）          目标场景清单（要产品拍板）         专项验收（最后统一测）
多开 + 通用 Hook    →    例如：钉钉 / 企微 / …      →    针对清单 App 测与修
```

- **若产品目标包含「钉钉相机替换」**：必须单独立项 **「钉钉专项」**（API 路径、活体、版本矩阵），**不能**用当前 PreviewCallback-only 默认当成已支持钉钉。  
- **若产品目标只是通用多开+伪装**：钉钉仅作 **可选抽检**，失败记兼容表，不阻塞功能代码收口。

**请产品尽快二选一（或排序）：**

| 选项 | 含义 |
|------|------|
| A. 通用优先 | 默认无指定办公 App；最后对「需要 hook 的 App 清单」逐个测 |
| B. 钉钉为首发卖点 | 在通用能力之上，增加 **钉钉专项** 里程碑（相机/定位路径以逆向+实测为准） |

**在未书面选定 B 之前，开发与 Review 默认按 A 执行。**

## 2. 现行测试与交付策略（你已确认）

| # | 要求 | 执行含义 |
|---|------|----------|
| **1** | **现阶段默认不做**模拟器/真机完整功能点按 | 不把「设备 PASS」当阶段门禁；禁止未测写 PASS |
| **2** | **现阶段先保证**：功能代码齐、**可打包、可安装、可启动** | 门禁 = `assembleDebug`（及约定的 `assembleRelease`）+ 冷启动进主界面不崩 |
| **3** | **最后统一**：对需要 Hook 的目标 App 清单做测试与修复 | 单独立项「目标 App 验收波次」，出问题再修，不穿插在每一 Phase 强制测钉钉 |

### 与 Phase 4 / F-01 的关系

- F-01「模拟器+真机回归」**整体后置**到「统一测试波次」，或降级为：  
  - **现在：** 构建 + 安装启动冒烟（可选，非强制全路径）  
  - **统一测试阶段：** 完整 F-01 + 目标 App 清单  
- 任何文档若写「真机 PASS」必须有真实点按记录；**无设备测试时只能写 Pending**。

### 统一测试阶段建议入口（四阶段代码齐后）

1. 安装启动与授权  
2. 多开基础（轻量 App）  
3. 伪装探针  
4. 相机（PreviewCallback 路径）  
5. **清单内目标 App**（若含钉钉：相机/打卡路径专项）

## 3. 开发与 Review 门禁（现阶段）

### 开发完成可宣称「代码交付」当且仅当

- [ ] 相关功能代码在 **main 已 commit**  
- [ ] `assembleDebug` 成功  
- [ ] 安装后 **能启动到主界面**（有设备时建议做；无设备时至少编译通过，并在说明中写「启动冒烟未做」）  
- [ ] **未**把未测功能写成设备 PASS  

### Review 现阶段关注

- 代码路径是否齐全、架构边界、已知限制是否文档化  
- **不**要求提交方提供钉钉/真机全绿（除非进入统一测试波次）  

### 禁止

- 未测宣称「钉钉可用 / 预览已是假图」  
- 未列清单却默认所有办公 App  

---

## 4. 一句话

> **sx 默认不是「钉钉专用」；通用多开+Hook 先把代码与可安装跑通，设备与目标 App（含是否做钉钉）放到最后统一测。钉钉若成卖点必须单独立项，不能靠当前默认实现默认同等 xh。**
